# VoiceStream 播放无声缺陷根因深度对抗讨论与修复方案

> 讨论焦点：针对 Opus 提出的“根因在于 `dropPlayers()` 与 `arm()` 的改动引入了副作用”论断进行底层逻辑、规范标准与执行链路的多维对抗复核。

---

## 1. 核心论点对抗与物理真相求证

### 1.1 论点一：`dropPlayers()` 改动的破坏性副作用（完全成立，且为直接元凶）

#### 变更前后对比
```typescript
// 加固前：直接调用 pause，保留 DOM 与 Web Audio 绑定关系
private dropPlayers(): void {
  if (this.raf) cancelAnimationFrame(this.raf);
  for (const p of this.players.values()) p.pause();
  this.players.clear();
}

// 加固后：调用异步 stop(0)，引发延迟级联销毁
private dropPlayers(): void {
  if (this.raf) cancelAnimationFrame(this.raf);
  for (const p of this.players.values()) {
    void p.stop(0); // 异步调用！
  }
  this.players.clear();
}
```

#### 物理失效因果链
1. **异步定时炸弹**：`TrackPlayer.stop(0)` 内部包含 `await sleep(Math.max(40, t * 1000))`，在 40ms 后执行 `this.a.release()`。
2. **`release()` 破坏音频管道**：
   ```typescript
   release(): void {
     this.audio.pause();
     this.audio.removeAttribute("src"); // 拔掉音频源
     this.audio.load();                 // 重置媒体元素
     this.file = null;
   }
   ```
3. **路由重入竞态 (Reentrancy Race Condition)**：
   * 用户在 `LibraryPage` 点击播放，触发首次 `engine.start()`，创建 `players` 并调用 `p.kick()`（此时正在异步拉取音频与预加载）；
   * `nav()` 同步跳转到 `PlayPage`，`PlayPage` 挂载时的 `useEffect` 执行。由于首次 `start()` 尚未完成 `await Promise.all(kicks)`，`engine.status` 依然是 `"idle"`；
   * `PlayPage` 的 `useEffect` 误判为未启动，在宏任务中发起了**第二次 `engine.start()`**；
   * 第二次 `start()` 调用 `dropPlayers()`，向第一次创建的正在加载/启动中的 players 投送了 `void p.stop(0)` 异步销毁指令；
   * 40ms 后，`release()` 触发，直接把正在向 Web Audio 输出 PCM 数据的 `HTMLAudioElement` 拔掉了 `src` 并 `load()`，音频流被物理斩断！

### 1.2 论点二：`arm()` 改动的副作用评估（部分成立，存在机制层错位）

#### 变更前后对比
```typescript
// 加固前：
arm(): void {
  if (!this.ctx || this.ctx.state === "closed") this.ctx = new AudioContext();
  if (this.ctx.state === "suspended") void this.ctx.resume();
}

// 加固后：
arm(): void {
  if (!this.ctx || this.ctx.state === "closed") this.ctx = new AudioContext();
  if (this.ctx.state === "suspended") void this.ctx.resume();
  try {
    const silent = this.ctx.createBuffer(1, 1, 22050);
    const src = this.ctx.createBufferSource();
    src.buffer = silent;
    src.connect(this.ctx.destination);
    src.start(0);
  } catch { /* ignore */ }
}
```

#### 机制层对抗推演：
1. **`AudioContext` vs `HTMLAudioElement` 的 Autoplay 策略分立**：
   * `silentBuffer.start(0)` 确实能无条件唤醒 `AudioContext` 硬件时钟（解决 Web Audio 的 Autoplay 限制）；
   * 但 VoiceStream 的音频底层是 `MediaElementAudioSourceNode`（依赖 `<audio>` 标签）。
   * 在现代浏览器（Chrome 71+ / Safari 11+）规范中，**`HTMLAudioElement.play()` 必须由直接的用户手势事件（User Activation）同步调用**。
2. **手势丢失与静音**：
   * 当由于路由竞态导致第二次 `start()` 在 React `useEffect` 中被异步触发时，它已经脱离了用户的直接点击事件调用栈。
   * 此时即使 `AudioContext` 处于 `running` 状态，脱离手势上下文的 `<audio>` 元素被浏览器静音或挂起，导致 `MixEngine` 时钟在走，但无声输出。

---

### 1.3 为什么“暂停再继续后，计时器归零并正常发声”？

这一现象完整验证了上述推演：
1. **首次进入**：受两次 `start()` 相互斩断与手势丢失影响，第一次计时器启动但音频源已死；
2. **用户点击暂停**：`toggle()` 捕获到 `st === "playing"`，调用 `engine.pause()`，停止已失效的播放；
3. **用户点击继续**：`toggle()` 在用户直接点击手势的调用栈中同步调用 `engine.start(mix, catalog)`：
   * 具备合法的直接用户手势；
   * `start()` 执行 `this.startedAt = performance.now()`，因此**计时器重新归零**；
   * 在 `PlayPage` 本地直接重新创建音轨，无跨页面路由跳转打断，不再触发二次 `dropPlayers`；
   * 音频正常发声。

---

## 2. 根治修复方案（两步闭环）

### 修复 1：移除破坏性的 `Slot.release()` 与异步 `stop(0)` 调用
* 在 `dropPlayers()` 中恢复直接同步 `p.pause()`，绝不对正在或即将使用的 `audio` 元素调用 `removeAttribute("src")` 与 `audio.load()`；
* 仅在整个引擎彻底销毁（`engine.stop()`）时才做彻底的资源清理。

### 修复 2：为 `MixEngine.start` 增加前置状态锁与去重保护
* 在 `engine.start()` 入口处，**同步**将状态置为 `"playing"`（或增加 `isStarting` 互斥锁）；
* 在 `PlayPage.tsx` 的 `useEffect` 中，若检测到 `engine.status === "playing"` 或当前正处于启动中，直接跳过，杜绝路由跳转造成的二次重复启动。
