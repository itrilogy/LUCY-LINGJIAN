| 阶段 | 核心论断与建议 | 底层逻辑依据 | 真实物理结果 | 结论定性 |
| :--- | :--- | :--- | :--- | :--- |
| **01 审计报告** | 建议对短音频改用 `AudioBufferSourceNode` 替代 `<audio>` 标签 | 物理限制：移动端硬件解码器配额（4~8 个）限制了 `HTMLAudioElement` 的并发 | 架构方向正确 | **无冲突** |

## 2. 冲突的底层根因剖析

### 为什么 02 备忘录的推导会与真实运行时冲突？

1. **混淆了“内存垃圾回收（GC）”与“Web Audio 节点生命周期”**：
   * 在普通 DOM 编程中，移除 `img.src` 或 `audio.src` 是释放内存的常见技巧；
   * 但在 Web Audio API 中，`ctx.createMediaElementSource(audio)` 将 C++ 底层的音频渲染图谱与 `<audio>` 绑定。在图谱未断开前调用 `audio.removeAttribute("src"); audio.load()`，会直接导致底层解码器进入不可逆的 Empty/Detached 状态。
2. **忽略了 React 路由跳转与状态机的异步重入竞态**：
   * 02 备忘录假设 `dropPlayers()` 仅在“旧播放结束、新播放开始”之间单向串行执行；
   * 实际物理链路中，`LibraryPage`（用户手势）发起 `start()` 与 `PlayPage`（`useEffect`）挂载存在几十毫秒的时间差，导致 `dropPlayers()` 变成了对正在启动的新实例的误杀。

## 3. 稳固无冲突的审计项清单

除上述关于 `Slot.release()` 的实现策略冲突外，其余所有审计与加固结论 100% 成立且稳固：

1. **安全层 (P0)**：
   * `:id` ULID 正则校验完全消除了路径遍历删除漏洞；
   * `safeJoin` 追加 `path.sep` 彻底封堵了 `SoundsWeb` 前缀绕过漏洞。
2. **数据层 (P1)**：
   * `writeMix` 的临时文件 + `renameSync` 保证了 POSIX 原子可靠性。
3. **渲染与状态层 (P2)**：
   * `MixEngine.tick` 10Hz 节流有效消除了 React 树 60fps 高频无意义重渲染；
   * `compositor.ts` 代数校验（`bgGen`）有效消除了切歌时的背景图覆盖竞态。
4. **音频架构终态方向**：
   * 01 报告提出的“根本解决方案是将短音频迁移到 `AudioBufferSourceNode`”依然是唯一正确的长期架构路线。
