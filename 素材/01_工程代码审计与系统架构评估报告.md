## 2. 安全与服务端审计

### 2.1 [P0] 路径遍历导致任意目录删除与任意文件读取

**源码证据：**

[`server/index.ts:56-59`](file:///Users/ic/Project/VoiceStream/server/index.ts#L56-L59):
```typescript
app.delete("/api/mixes/:id", (c) => {
  const ok = deleteMix(ROOT, c.req.param("id"));
```

[`server/mixes.ts:5-6`](file:///Users/ic/Project/VoiceStream/server/mixes.ts#L5-L6):
```typescript
export function mixDir(root: string, id: string): string {
  return path.join(root, "data/mixes", id);  // id 未校验
}
```

[`server/mixes.ts:48-52`](file:///Users/ic/Project/VoiceStream/server/mixes.ts#L48-L52):
```typescript
export function deleteMix(root: string, id: string): boolean {
  const dir = mixDir(root, id);
  if (!existsSync(dir)) return false;
  rmSync(dir, { recursive: true, force: true });  // 递归强制删除
  return true;
}
```

**攻击路径**：`DELETE /api/mixes/..%2F..%2Fsrc` → `path.join(ROOT, "data/mixes", "../../src")` → 解析为 `ROOT/src` → `rmSync` 递归删除源码目录。

**同一漏洞影响范围**：
* `GET /api/mixes/:id` → `readMix` → 可读取 `data/mixes/../../` 下任意 `mix.json` 文件（信息泄漏风险较低，因为要求文件名恰好为 `mix.json`）
* `PUT /api/mixes/:id` → `writeMix` → 可在任意目录创建 `mix.json` 文件。但此路由有部分防护：Zod 校验 `parsed.data.id !== id` 要求 body 中 id 与 URL 中 id 一致，而 id 必须匹配 ULID 正则 `^[0-9A-HJKMNPQRSTVWXYZ]{26}$`，**因此 PUT 路径上路径遍历被 Zod schema 间接阻断**

**修复方案**：在路由处理层统一增加 id 格式校验中间件：
```typescript
const ULID_RE = /^[0-9A-HJKMNPQRSTVWXYZ]{26}$/;
function validateId(c: Context, next: Next) {
  if (!ULID_RE.test(c.req.param("id"))) return c.json({ error: "invalid_id" }, 400);
  return next();
}
```

### 2.2 [P0] 静态资源路径前缀匹配穿透

**源码证据**：

[`server/static.ts:21-25`](file:///Users/ic/Project/VoiceStream/server/static.ts#L21-L25):
```typescript
function safeJoin(root: string, rel: string): string | null {
  const resolved = path.resolve(root, rel);
  if (!resolved.startsWith(path.resolve(root))) return null;
  return resolved;
}
```

**物理事实**：`path.resolve(root)` 不以 `/` 结尾。若 `root` 为 `/app/asset/Sounds`，则 `/app/asset/SoundsWeb/secret.m4a` 也满足 `startsWith("/app/asset/Sounds")`。当前工程 `.gitignore` 中恰好有 `asset/SoundsWeb/` 目录，说明该同前缀目录确实存在于实际部署环境中。

**攻击路径**：`GET /sounds/../SoundsWeb/secret.m4a`。其中 `decodeURIComponent` 后 raw 为 `../SoundsWeb/secret.m4a`，`path.resolve("/app/asset/Sounds", "../SoundsWeb/secret.m4a")` = `/app/asset/SoundsWeb/secret.m4a`，满足 `startsWith("/app/asset/Sounds")`，通过校验。

**修复方案**：
```typescript
function safeJoin(root: string, rel: string): string | null {
  const resolvedRoot = path.resolve(root);
  const resolved = path.resolve(root, rel);
  if (!resolved.startsWith(resolvedRoot + path.sep) && resolved !== resolvedRoot) return null;
  return resolved;
}
```

## 3. Web Audio 音频引擎审计

### 3.1 Crossfade 等功率曲线 — 声学验证通过

[`MixEngine.ts:29-33`](file:///Users/ic/Project/VoiceStream/src/audio/MixEngine.ts#L29-L33):
```typescript
function cosineDown(from: number, n = 48): Float32Array {
  return Float32Array.from({ length: n }, (_, i) => from * Math.cos((Math.PI / 2) * (i / (n - 1))));
}
function cosineUp(to: number, n = 48): Float32Array {
  return Float32Array.from({ length: n }, (_, i) => to * Math.sin((Math.PI / 2) * (i / (n - 1))));
}
```

声学分析：
* 淡出曲线 $g_{out}(t) = A \cdot \cos(\frac{\pi}{2} t)$，淡入曲线 $g_{in}(t) = B \cdot \sin(\frac{\pi}{2} t)$
* 对于非相干源：总功率 $P = g_{out}^2 + g_{in}^2 = A^2\cos^2 + B^2\sin^2$
* 当 $A = B$（均为 1）时 $P = 1$，常功率无响度凹陷
* **采用 `setValueCurveAtTime` 在音频线程硬件时钟上执行**，不受主线程节流影响。曲线本身的声学行为是正确的

### 3.2 [P1] 后台标签页 setInterval 节流

**源码证据**：[`MixEngine.ts:253-268`](file:///Users/ic/Project/VoiceStream/src/audio/MixEngine.ts#L253-L268)

`armWatch` 使用 `window.setInterval(() => {...}, 120)` 轮询播放进度，当 `remain <= tout + 0.05` 时触发 `crossfade`。

**后台行为分析**：
1. Chromium 后台标签页将 `setInterval` 最小间隔强制提升至 1000ms（有的场景下更长）
2. 假设 `fade_out_ms = 2000`（即 tout = 2s），原本需在剩余 2.05s 时触发。在 1000ms 轮询间隔下，可能在剩余 1.05s 时才首次检测到，导致实际淡出时间从 2s 缩短到 1s
3. 更极端情况：Chrome 的 "Intensive throttling" 可将后台 timer 降至每分钟一次（Background tab > 5min），此时完全错过淡出窗口

**但需注意的缓解因素**：
* `TrackPlayer` 在 L128-129 注册了 `ended` 事件监听。即使 timer 错过了淡出检测点，`ended` 事件仍会触发 `crossfade(true)`。也就是说不会完全死寂，但确实会出现**前曲结束 → 静音间隙 → 下曲开始**的音频断层，破坏无缝过渡

**建议**：使用 Web Worker timer 或预计算淡出起始点后用 `setTimeout` 在 Worker 中调度。

### 3.3 [P2] 多 HTMLAudioElement 实例移动端兼容

**源码精确分析**：
* `Slot` 类在构造时创建 `HTMLAudioElement` + `MediaElementAudioSourceNode`（[`MixEngine.ts:41-51`](file:///Users/ic/Project/VoiceStream/src/audio/MixEngine.ts#L41-L51)）
* 每个 `TrackPlayer` 持有 2 个 Slot（[L121-122](file:///Users/ic/Project/VoiceStream/src/audio/MixEngine.ts#L121-L122)）
* 最多 8 条轨道（Zod schema `z.array(TrackSchema).max(8)`），所以最多 16 个 `MediaElementAudioSourceNode`
* `MixEngine.start` 会先调用 `dropPlayers()` 释放旧的（[L402](file:///Users/ic/Project/VoiceStream/src/audio/MixEngine.ts#L402)），**不存在跨会话累积**
* 但 `dropPlayers` 仅调用 `p.pause()`，**没有释放 MediaElementAudioSourceNode**。一旦 `AudioContext` 创建了 `createMediaElementSource`，该 source 无法断开关联。这意味着即使调用 `stop()` → `ctx.close()`，中间短暂的窗口内 16 个 source 仍活跃

**iOS Safari 硬限制**：iOS 通常允许 4-8 个并发 audio 元素解码。满载 8 轨 16 元素时，后创建的元素可能静默失败或抢占前序轨道。

**建议**：对 `playback: "buffer"` 类短音频（<15MB）改用 `AudioBufferSourceNode`，仅对 `"stream"` 类长音频保留 `HTMLAudioElement`。

### 3.4 [P3 新发现] volumeToGain 方形律精度

[`src/audio/volume.ts:4-8`](file:///Users/ic/Project/VoiceStream/src/audio/volume.ts#L4-L8):
```typescript
export function volumeToGain(v: number): number {
  const x = Math.min(1, Math.max(0, v));
  if (x <= 0) return 0;
  return x * x;
}
```

方形律 ($gain = v^2$) 是合理的感知响度映射。但注释中声称 "50% 约等于 -6 dB" 不够精确：$20 \log_{10}(0.5^2) = 20 \log_{10}(0.25) \approx -12\text{dB}$，不是 -6 dB。-6 dB 对应的是 $v^1$ 线性映射时 50% 的结果。注释有误导性，但不影响功能。

### 3.5 [P3 新发现] `MixEngine.tick` rAF 循环仅驱动 UI 更新

[`MixEngine.ts:514-517`](file:///Users/ic/Project/VoiceStream/src/audio/MixEngine.ts#L514-L517):
```typescript
private tick = (): void => {
  this.emit();
  if (this.status === "playing") this.raf = requestAnimationFrame(this.tick);
};
```

`tick` 每帧调用 `emit()`，后者调用 `snapshot()` 并通知所有 listener。`snapshot()` 内部遍历所有 player 计算 `progress()`。在播放状态下这意味着**每秒 60 次全量 snapshot 计算与 React setState 调用**。对于一个音频播放器而言，5-10fps 的 UI 更新频率已经足够（进度条变化速度极慢）。当前实现产生约 6 倍的不必要渲染开销。

### 4.3 [P3] Canvas 2D 粒子系统 GC 压力

**源码证据**：[`compositor.ts:743`](file:///Users/ic/Project/VoiceStream/src/effects/compositor.ts#L743)

```typescript
this.particles = this.particles.filter((p) => { ... });
```

每帧 `draw` 方法中：
1. `filter` 创建一个新数组，丢弃旧数组
2. `spawn*` 方法（`spawnRain`, `spawnFly`, `spawnGlass` 等）每次 `push` 一个新对象字面量
3. 在 `raindrops` 效果下，L394 `this.particles = this.particles.filter(...)` 对 glass 碰撞也重建数组
4. 粒子上限：rain 40 + glass 170 + ring 8 + embers 90 + fireflies 48 + parallax 28 + grain 36 ≈ 最多 420 个粒子对象

实际影响：V8 的 Minor GC 在现代桌面浏览器上处理 420 个短生命周期对象通常在 1ms 以内，**在桌面端这不是性能瓶颈**。但在低端移动设备上可能引发间歇性帧率波动。

**建议**：仅当项目目标包含移动端时才需优化。优化方向为对象池（Object Pool）+ TypedArray 存储粒子状态。

## 6. 数据模型与 ULID 实现审计

### 6.1 [P3 新发现] ULID 随机部分熵损失

[`shared/ulid.ts:12`](file:///Users/ic/Project/VoiceStream/shared/ulid.ts#L12):
```typescript
for (const b of bytes) rand += C[b % 32];
```

`b` 为 0-255 的 Uint8，`b % 32` 将 256 个值映射到 32 个桶。由于 256 不是 32 的整数倍…等等，256 / 32 = 8，**恰好整除**。每个桶有 8 个值映射到它，分布均匀。熵损失分析：每字节 8 bits → 每字符 5 bits（$\log_2 32 = 5$），16 字节 → 16 字符 × 5 bits = 80 bits 随机性。标准 ULID 随机部分为 80 bits（16 字符 × 5 bits），所以**熵保留正确**。

但有一个问题：代码生成 16 字节 → 16 字符随机部分，然后与 10 字符时间部分拼接后 `slice(0, 26)`。总共 10 + 16 = 26，恰好不需要截断。**实现正确**。

### 6.2 Zod Schema 严格模式 — 良好实践

[`shared/mixSchema.ts`](file:///Users/ic/Project/VoiceStream/shared/mixSchema.ts) 在 `TrackSchema` 和 `MixSchema` 上都使用了 `.strict()`，拒绝未知字段。这防止了客户端注入额外属性绕过校验。
